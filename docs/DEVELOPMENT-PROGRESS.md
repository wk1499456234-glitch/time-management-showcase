# AI活用開発で得られた知見

TimeWeaveは、取り組んだ時間と実際にできたことを一緒に残すために作り始めた。要件や画面の方向は自分で決め、AIとの対話で整理し、Codexに実装やテスト、実行環境の整備を依頼した。ここでは、開発で役立った三つの進め方と、実際に使ってもらうことを考える中で気づいた一つの注意点をまとめる。

## 開発手順と進捗をMarkdownに残す

会話だけでは、どこまで決まり、何が実装されたのかを追いにくかった。そこで、AIと決めた開発手順、要求、決定の理由、現在の進捗を、それぞれの役割を持つMarkdownに残した。手順は[開発手順・作業再開ガイド](DEVELOPMENT-WORKFLOW.md)、要求や設計は製品資料、日々の決定と進捗は非公開の開発主記録で管理している。実行環境や保存先の違いも記録し、作業対象を取り違えないようにした。

チャットが中断したり、新しいウィンドウに移ったりしたときは、まずAIに関連ファイルを読ませ、完了した仕事と次に行うことを整理してもらう。実際のコードや作業状態との照合はCodexが行い、その説明を自分が確認してから続ける。この分担により、以前の会話の内容をそのまま現在の状態として扱わずに作業を再開できる。

この方法で、同じ説明を繰り返す負担や、決めた条件の見落としを減らしやすくなった。古い計画を実装済みの機能と取り違えることも防ぎやすい。AIがすべてを記憶するのではなく、必要な情報を読み直して、現物と確かめられるようにしている。

## 実装前に画像でUIのイメージを共有する

画面を作る前に、相談用のAIと考えを整理し、AIに画面のイメージ画像を生成してもらった。画像を見ながら配置や雰囲気を調整し、方向が決まってから開発を担当するAIであるCodexへ実装を依頼した。言葉だけでは伝えにくい余白、情報の優先順位、全体の印象を共有しやすかった。

実装前に方向をそろえることで、最初の画面を期待に近づけ、実装後の修正のやり取りを減らすことを目指した。手戻りと、それに伴うAIの処理量を抑える目的もあったが、削減量を数値で測ったわけではない。画像は方向を確認するためのもので、一度生成すれば完成するわけではなく、実際の画面で操作を確かめる必要がある。

## AIの検証と実際の操作を組み合わせる

パソコン向けの初期画面は、複数の機能を一つのページに並べ、メニューを押すと該当箇所へスクロールする構成だった。入口やボタンの重複を減らすため、「タイマー」「記録」「AI振り返り」「設定」の四ページに整理し、活動の選択から時間の計測、成果入力へ進む操作順も見直した。

スマートフォンでは、成果の確認入口や分類名が分かりにくく、比較表の改行が読みにくいことに気づいた。スクリーンショット、操作手順、期待する見え方をAIへ伝え、確認ボタンや分類の選択、週ごとにまとめた比較表示へ改善した。修正後も画面を開き、操作の流れと読みやすさを確かめた。

AIにテストを実行させる際は、確認した内容と結果を説明させた。そのうえで、自分でも保存・再読み込み・画面切り替えなどの操作を試した。実際に使うことで、ボタンの見つけにくさや表示の崩れも見つかったため、プログラムの検証と利用者としての確認を組み合わせることが重要だと分かった。

これは基本的な確認作業だが、実際に操作すると、AIのチェックでは見落とされていたボタンの探しにくさ、操作のつながりの悪さ、表示の問題に気づけた。

ここで述べたのは実際に試した操作から得た経験であり、すべての端末や操作の検証が完了したという意味ではない。確認した範囲と結果は[検証記録](VALIDATION.md)に分けて残している。

## 利用条件も早い段階で考える

開発中はAI機能を動かすことに意識が向き、ほかの人が実際にどう使うかを十分に考えられていなかった。新しい成果の整理や振り返りの作成には、AIサービスとそれを接続する実行環境が必要で、費用の負担先やアカウントの権限も決めておく必要がある。

現在の公開URLでは時間と成果を記録でき、あらかじめ生成・保存したAIのサンプルを読める。ほかの人が自分の記録を新たにAIで整理したり、振り返りを作成したりするには、費用、アカウント、接続先の環境を別途相談する必要がある。この経験から、何を作るかだけでなく、誰がどの条件で使えるかも早い段階から一緒に考えることが大切だと分かった。
