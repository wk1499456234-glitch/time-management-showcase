# AI活用開発で得られた知見

TimeWeaveは、取り組んだ時間と実際にできたことを一緒に残すために作り始めた。要件や画面の方向は自分で決め、AIとの対話で整理し、Codexに実装やテスト、実行環境の整備を依頼した。その中で役立ったのは、作業を再開できる記録を残すことと、AIの検証に自分の操作を重ねることだった。

## 開発手順と進捗をMarkdownに残す

会話だけでは、どこまで決まり、何が実装されたのかを追いにくかった。そこで、AIと決めた開発手順、要求、決定の理由、現在の進捗を、それぞれの役割を持つMarkdownに残した。手順は[開発手順・作業再開ガイド](DEVELOPMENT-WORKFLOW.md)、要求や設計は製品資料、日々の決定と進捗は非公開の開発主記録で管理している。実行環境や保存先の違いも記録し、作業対象を取り違えないようにした。

チャットが中断したり、新しいウィンドウに移ったりしたときは、まずAIに関連ファイルを読ませる。その後、実際のコードや作業状態と照合して、今の依頼、完了したこと、次に行うことを確認してから続ける。以前の会話の内容をそのまま現在の状態として扱わないことが大切だった。

この方法で、同じ説明を繰り返す負担や、決めた条件の見落としを減らしやすくなった。古い計画を実装済みの機能と取り違えることも防ぎやすい。AIがすべてを記憶するのではなく、必要な情報を読み直して、現物と確かめられるようにしている。

## AIの検証と実際の操作を組み合わせる

パソコン向けの初期画面は、複数の機能を一つのページに並べ、メニューを押すと該当箇所へスクロールする構成だった。操作の入口やボタンが重複し、何をどこで行うかが分かりにくかったため、「タイマー」「記録」「AI振り返り」「設定」の四ページに整理した。時間を測る画面では、活動の選択、時間の表示、開始・一時停止・終了、成果入力の順に操作できるよう、情報の置き方も見直した。

スマートフォンでは、実際に使ってみると成果の確認入口が見つけにくく、分類名の意味が分かりづらいことや、履歴の比較表が細かく折り返されて読みにくいことが分かった。AIへ修正を依頼するときは、スクリーンショットだけでなく、そこに至る操作手順と期待する見え方を合わせて伝えた。確認ボタンや分類の選択、週ごとにまとめた比較表示へ直した後も、画面を開いて操作の流れと読みやすさを確かめる形にした。

AIにテストを実行させる際は、確認した内容と結果を説明させた。そのうえで、自分でも保存・再読み込み・画面切り替えなどの操作を試した。実際に使うことで、ボタンの見つけにくさや表示の崩れも見つかったため、プログラムの検証と利用者としての確認を組み合わせることが重要だと分かった。

ここで述べたのは実際に試した操作から得た経験であり、すべての端末や操作の検証が完了したという意味ではない。確認した範囲と結果は[検証記録](VALIDATION.md)に分けて残している。
