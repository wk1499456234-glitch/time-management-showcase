# 開発手順・作業再開ガイド

## この文書の役割

TimeWeaveの公開リポジトリで合意した開発手順と、チャットが中断したときの再開方法をまとめる。AIが過去の会話をすべて覚えていることを前提にせず、決定と状態をファイルに残して読み直す。

この文書は操作権限を与えるものではない。ユーザーの今回の指示、作業環境の`AGENTS.md`、安全・承認規則を引き続き守る。非公開の元プロジェクトにある製品仕様やAgent管理の規則を置き換えず、この公開版の作業手順を担当する。

## 1. 開発の流れ

**要件確認 → 範囲の確定 → 実装 → 対象を絞った検証 → 画面確認 → 公開 → 記録更新**

| 段階 | 行うこと | 次へ進むための材料 |
| --- | --- | --- |
| 要件確認 | 実際の操作、問題、期待する結果を確認し、現行コードと資料を読む | 対象者・問題・期待結果が分かる |
| 範囲の確定 | 変更するもの、保持するもの、受け入れ条件、権限を記録する | 作業対象と完了条件が明確 |
| 実装 | 確認した範囲だけを変更する。既存の未コミット作業を保全する | 理由を説明できる差分 |
| 変更対象の検証 | 変更に対応したテスト、型検査、ビルド、公開範囲のチェックを実行する | 実行コマンド、結果、未実施項目 |
| 画面確認 | 必要な状態・言語・画面幅で操作し、展開後と編集中も確認する | スクリーンショット、操作結果、実機との区別 |
| 公開 | 承認された範囲だけをコミット・通常pushし、Pagesの実行と配信物を確認する | コミット、成功した実行、HTMLとリソースの一致 |
| 記録更新 | 日常の状態・引き継ぎは非公開の主記録、検証・公開は技術資料へ残す。経験ページは新しい知見があるときだけ更新する | 各資料の役割が分かれ、作業を再開できる状態 |

問題調査から始まる修正でも、実装前に現物を確認する。文書・注釈だけの変更では、無関係な画面の全面再検証や有料AI呼び出しを増やさず、文書の整合性と実行内容の不変性を確認する。

## 2. 役割

| 担当 | 責務 |
| --- | --- |
| 作者 | 利用場面、優先順位、採用する仕様と画面の方向を判断し、実際の使用結果を確認する。公開や費用等の権限を決める |
| 相談用のAI | 要件の整理、選択肢の比較、計画や依頼文の整理を支援する。作者の判断や検証結果を代行したと断定しない |
| Codex | 指定資料と現物を調べ、許可された範囲で実装・テスト・環境操作を行い、差分と結果を報告する |

タスクは「目標、変更範囲、保持条件、検証方法」で伝える。実機でしか分からない操作や外部の権限が必要な作業は、その不足を具体的に記録し、ほかの実行可能な作業を進める。

## 4. 一回の作業を終えるとき

記録先を内容に応じて分ける。経験ページへ毎回の作業報告を追記しない。

- **非公開の開発主記録**：確定した決定と理由、保持条件、実際の変更、未完了項目、次の作業、ソース・実行版と公開状態を残す。既存の主記録を継続して使う。
- **検証記録**：実行した確認の対象、環境、結果と未実施の範囲を残す。詳細な非公開ログは主記録から参照する。
- **公開手順**：ビルド・公開・配信ファイルの照合・復旧方法を維持する。公開の実行結果は検証記録と該当Workflowで追跡できるようにする。
- **経験ページ**：ほかの人にも役立つ新しい経験が得られたときだけ更新する。問題、AIとの進め方、実際に確かめたことを簡潔に説明し、毎回のコミット番号・テスト件数・公開履歴は載せない。

状態は**検討済み／実装済み／検証済み／公開済み**に分ける。テスト合格を実機合格としない。ローカルコミットを公開済みとしない。ページがHTTP 200を返すだけで新しい版の配信を断定しない。自分自身のコミット番号を含められない文書では、公開識別子と対応するWorkflowの`head_sha`で照合する。

## 5. 新しいチャットから再開する

1. 作業環境の規則、本書、READMEと今回の変更に関係する要件・記録定義・設計、検証記録、公開手順を読む。経験ページは進め方を参考にするときに読み、現在の進捗の根拠にはしない。
2. 作業対象のディレクトリを確認し、`git branch --show-current`、`git status --short`、`git log -5 --oneline`、`git diff`で現状を調べる。未コミットの変更を残し、過去の番号へ一律に戻さない。
3. 権限の範囲で最新のリモートの`main`とPagesの実行を調べ、実際のHTML識別子・リソースと照合する。ソース、ローカルのビルド成果物、配信中の版を混同しない。
4. 今回の依頼、公開資料、実際のGit・公開状態から、完了したことと次の作業を確認する。非公開環境では、そこで案内された既存の主記録も読み、資料とコードの違いを確かめる。非公開資料にアクセスできない場合、経験ページから不足する進捗を推測しない。
5. 今回許可された範囲で続行し、完了時は第4節の分担に従って記録する。別チャットを開くこと自体は、公開・支出・個人データへの操作の追加承認にはならない。

```text
TimeWeaveの作業を続けてください。
まず適用されるAGENTS.md、docs/DEVELOPMENT-WORKFLOW.md、README.mdを読み、
今回の変更に関係するREQUIREMENTS、RECORD-DEFINITION、DESIGN、
VALIDATION、DEPLOYMENTを確認してください。
実際のブランチ、作業ツリー、最近のコミット、リモートと公開状態を照合し、
既存の変更を保全してください。資料とコードの違いは先に確認してください。
非公開環境では、そこで案内された既存の開発主記録も確認してください。
経験ページは方法を参考にする資料であり、現在の進捗の根拠にはしないでください。
今回の依頼、確認できた成果、未確認事項と次の一手を説明したうえで、
明示した範囲で続行してください。日常の状態と引き継ぎは非公開の主記録、
検証と公開情報は対応する技術資料へ残し、経験ページは新しい知見があるときだけ更新してください。

今回の目標・変更範囲：［記入］
保持するもの・完了条件：［記入］
今回許可する操作：［記入］
```

## 6. 公開資料と非公開資料

公開資料は製品の使い方、共有できる経験、検証・公開の要約を扱う。日常の進捗や具体的な引き継ぎは非公開の主記録で管理し、公開の作業再開ガイドにはその場所や内容を書かない。個人データ、資格情報、非公開接続先、詳細な操作ログ、私的な設定は公開しない。公表用の話す順序や私的な予定は製品資料の役割ではない。

非公開の開発主記録には、この公開手順への参照、実行証拠、運用上の引き継ぎと次の操作を残す。同じ手順を別の場所へ複製して更新元を増やさない。公開前はファイル一覧・ハッシュ・全テキスト検査に加え、実際の差分を人が確認する。パターン検査だけであらゆる機密情報を検出できるとは考えない。
